open-Xdownload 是自托管的 X/Twitter 媒体下载和归档工具。Go 服务负责认证、任务调度、X API 请求、下载和 SQLite 存储；React 前端负责任务、计划、媒体库和配置。

### 1. [P2] 改名的最后一次实体写入失败，账号文件长期分散到两个目录

**位置：** [manager.go:1745](internal/jobs/manager.go:1745)、[manager.go:1767](internal/jobs/manager.go:1767)；失败重试读取旧目录为 [manager.go:1578](internal/jobs/manager.go:1578)。

- **这段代码做什么：** X 用户显示名变化后，移动归档目录，并更新媒体记录的磁盘路径。
- **问题与触发：** `Alice(alice)` 改为 `Alice2(alice)`，目录移动和下载路径重写先成功，但随后实体名称写入失败。数据库恢复后，失败媒体重试按旧实体名重新创建旧目录；以后改名又遇到已经存在的新目录，两个目录不再自动收敛。
- **证据：** 仅注入最后实体写入失败，撤销故障，再执行失败媒体重试和四次目录准备，实体仍叫 `Alice(alice)`，磁盘同时存在旧、新目录。普通及竞态定点测试均复现。
- **最小修复：** 下载路径重写与实体名称更新使用同一数据库事务；失败时补偿目录移动。用户和列表实体一起修正。
- **不修的后果：** 历史文件和后续重试文件长期分散，目录归属、列表链接与数据库不一致。

现有测试未覆盖“最后实体写失败后，先运行失败媒体重试”的顺序。

### 2. [P2] 不可用媒体的“二次确认”实际只请求一次，临时 404 导致漏归档

**位置：** [manager.go:869](internal/jobs/manager.go:869)、[manager.go:822](internal/jobs/manager.go:822)、[storage.go:2464](internal/storage/storage.go:2464)；重试分类为 [manager.go:1688](internal/jobs/manager.go:1688)。

- **这段代码做什么：** 想通过两次独立失败确认媒体永久不可用，避免 CDN 短暂 404 被缓存半年。
- **问题与触发：** 首次 404 写入带“首次观察”的 `unavailable_media` 行并返回原错误；读侧只判断行存在，就在下一次网络请求之前直接跳过。原始 404 又被判为不重试，因此没有进入失败推文队列。
- **证据：** 固定快照中，本地服务器只第一次返回 404，此后都可返回有效媒体；再调用三次，HTTP 请求数仍为 1，下载记录为空、磁盘无文件。通过归档入口也得到 `failed_queue=0`、`incremental_cursor=100`。现有 DMCA 测试同样失败：`HTTP requests after second download = 1, want 2`。
- **最小修复：** 区分待确认与已确认不可用，只有已确认项允许入口跳过。首次观察必须可重试，第二次实际请求仍失败才确认；成功则清除待确认记录，并处理已有“首次观察”行。
- **不修的后果：** 已恢复媒体仍被跳过，增量游标已经前进且无补偿队列，之后不会自动补齐。

不可用记录有 180 天保留清理，不是永不删除；但清理不会回退游标或补建失败队列。

### 3. [P2] 独立置顶推文被排在页尾，增量归档提前停页

**位置：** [client.go:1642](internal/xclient/client.go:1642)、[client.go:1690](internal/xclient/client.go:1690)；早停判断为 [client.go:745](internal/xclient/client.go:745)、[client.go:783](internal/xclient/client.go:783)。

### 4. [P2] 终态保存三次都失败后，任务没有工作协程却一直显示运行中

**位置：** [manager.go:1895](internal/jobs/manager.go:1895)；退出清理 active 为 [manager.go:440](internal/jobs/manager.go:440)。

- **这段代码做什么：** 保存任务终态，并在任务函数退出时释放执行名额。
- **问题与触发：** 文件和下载记录均成功，但数据库故障持续覆盖最终状态的三次保存尝试。累计约 1.5 秒退避后只记日志，协程退出，数据库仍为 `downloading`；恢复后的调度只领取 `pending`，普通重试也拒绝仍被认为活跃的任务。
- **证据：** 撤销故障后再执行三次调度，任务仍为 `downloading`，`active=0`、可用槽位为 1，普通重试被拒绝。
- **最小修复：** 重试耗尽后仍保留可恢复的收尾流程，让调度器继续完成终态持久化或修复残留状态，不能只移除 active。
- **不修的后果：** 幽灵任务长期显示运行中，依赖它完成的计划也可能停住；取消后重试或重启可人工恢复。

并发改动增加了有限重试，已缓解一次短暂失败，但未解决重试耗尽后的状态恢复。

### 5. [P2] 同推文第一个媒体持续失败，后面的已恢复媒体永远轮不到重试

现有测试没有覆盖一条推文内不同媒体分别恢复的情形。

### 15. [P2] 5 万条媒体的“未识别用户”筛选，第一页耗时约 25 秒

**位置：** [library_page.go:391](internal/storage/library_page.go:391)，窗口排名为 [library_page.go:348](internal/storage/library_page.go:348)。

- **这段代码做什么：** 筛选无用户目录归属的媒体，并计算分页总数。
- **问题与触发：** 每批 512 条重新执行完整 ROW_NUMBER 去重、排序，再增加 OFFSET；即便只展示第一页，为计数也要扫完整个库，5 万条约重复 98 次全量计算。
- **证据：** 同机临时库：1.2 万条时 all 约 60ms、unknown 约 1.25s；5 万条时分别约 453ms、24.98s。结果条数正确，测试未创建大量媒体文件，耗时主要来自重复 SQL。
- **最小修复：** 一次查询流式读取去重结果，在 Go 中判断归属和累计总数，只保留当前页需要的条目。

时间是本机测量，不是所有部署的固定耗时。源码虽注明该筛选少用，但 5 万条已触及明显退化，不是微小优化。
